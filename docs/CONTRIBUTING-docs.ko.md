# smocket 문서 작성 지침 (초안)

> 작성: 2026.07.28
> 대상: `docs/` 아래 신규 문서 전체
> 성격: 작업 지침. 사람과 Claude Code 양쪽이 참조.

---

## 0. 독자

프로그래밍은 알지만 **socket.io 경험은 없을 수 있는** 개발자를 독자로 둡니다.

- 언어 문법, 비동기, 자료구조, 마이크로태스크 큐 같은 일반 개념은 안다고 간주합니다.
- room, namespace, adapter, ack 같은 socket.io 고유 개념은 모른다고 간주합니다.

---

## 1. 문체

- **열거물은 불릿을 사용하세요.** 선택지와 필드 목록, 규칙 목록과 대안 목록은 불릿을 사용합니다.
- **인과는 산문으로 작성합니다.** "왜 이 결론인가"는 2~4문장으로 씁니다. 문단 하나에 주장 하나씩입니다.
  - 불릿으로 조각내면 A와 B는 남지만 _A라서 B_, 즉 인과가 사라집니다. 결정 기록에서 이건 좋지 못합니다.
- **비유를 절대적으로 금지합니다.** 설명이 막히면 비유 대신 최소 코드 예제 또는 실제 동작 한 줄을 적어주세요.
  - 예외: `room` / `namespace` / `broadcast` / `adapter` 등은 비유가 아니라 socket.io의 실제 API 이름입니다. 그대로 사용합니다.
  - 설명을 위한 새로운 비유를 금지합니다.

---

## 2. 용어

**원칙: 독자가 모를 수 있는 단어를, 절대 설명 없이 지나가지 않아야 합니다. 단, 기본 처리는 정의가 아니라 링크입니다.**

| 종류                                                                | 처리                                                                                          |
| ------------------------------------------------------------------- | --------------------------------------------------------------------------------------------- |
| socket.io 도메인 용어 (room, namespace, adapter, ack, handshake)    | `glossary.md`에 정의합니다. 각 문서는 첫 등장에 한 번 링크하며, 본문에서 재정의하지 않습니다. |
| smocket 고유 개념 (배달 Fidelity, dual-run, Marker 증명, 이탈 목록) | 그 개념을 다루는 문서에서 정의. 다른 문서는 링크로 나타냅니다.                                |
| 그 문서에서만 쓰는 말 (seam, claim queue 등)                        | 첫 등장 자리에서 한 줄 설명. 링크할 곳이 없는 경우가 여기에 속합니다.                         |
| 일반 프로그래밍 용어 (microtask, FIFO)                              | 설명하지 않습니다.                                                                            |

- 어느 갈래인지 애매하면 **glossary에 넣습니다.** 중복 정의보다 위치가 어색한 정의가 낫습니다.
- 이 규칙이 §5의 60줄 제한을 실제로 지켜지게 합니다. 정의를 본문에 쓰지 않기 때문입니다.

---

## 3. 내용

- **결정의 이유는 "socket.io는 이렇게 한다"에서 출발합니다.** 이 프로젝트에서 설계 질문의 첫 발걸음은 실물과의 대조이며, 문서도 그 순서를 보여야 합니다.
- **버린 대안을 반드시 적습니다.** 무엇을 골랐는지만 있으면 같은 논쟁이 다시 열릴 수 있으며, 새로운 논쟁에서 더 좋은 설계를 위한 재료로서 활용될 수 있습니다.
- **틀린 것으로 밝혀진 배제 사유는 지우지 말고 철회 표시를 남깁니다.** (결정 1 C안 문서의 "철회한 배제 사유 2건"이 이 형태를 따릅니다.)
- **"확인되지 않음"과 "없음"을 구분합니다.** 확인하지 못한 것을 절대로 없다고 쓰지 않습니다.
- socket.io 소스 인용은 짧게 합니다. 가능하다면 인용 대신 동작 서술로 대체합니다.

---

## 4. 금지

- 금지 사항은 최소화합니다. _"코끼리는 생각하지 마"_
- **상태값의 작성.** 테스트 개수, 통과율, 진행률, "현재 구현 중" 같은 값. 그건 CI와 이슈의 몫이고, 문서에 박히면 red일 때 거짓말이 됩니다.
- **기능 목록의 나열.** 기능이 늘 때마다 손으로 고쳐야 하고, 안 하면 조용히 틀린 문서가 됩니다.

## 6. TL;DR 블록

모든 문서 최상단에는 반드시 TL;DR이 작성되어야 합니다.

- **가급적 3줄 이내로 작성해주세요.** 다만 결론이 잘릴 것 같으면 넘겨도 괜찮습니다. 길이보다는 완결성을 우선해주세요.
- 담을 것은 세 가지입니다. **무엇으로 결정했는가 / 왜 그런가 / 그래서 이 문서의 결론은 무엇인가.**
  - 결정과 결론은 다릅니다. `0005`의 결정은 "connect_error를 쏜다"이고, 결론은 "여기가 실물과 의도적으로 갈라지는 유일한 지점"입니다. 후자가 `differences.md`로 이어지는 고리이므로, 줄 수가 모자랄 때 잘라내면 안 되는 것이 이 줄입니다.
- 본문에 없는 새 정보를 담지 않습니다.

```markdown
# 0005. Missing server: connect_error, immediately, no retry

**Status:** Accepted · 2026-07-22 · #40
**Governed by:** [0000](./0000-do-not-invent-what-has-no-source.md)

> **TL;DR** — When no server is registered for the origin, smocket fires
> `connect_error` on the next tick and logs to the console. It does not throw,
> and it does not retry. Real socket.io retries forever; this is the one place
> the two deliberately differ.
```

초안 단계에서는 **TL;DR · Decision · Alternatives rejected** 세 칸만 채웁니다. Context와 Consequences는 비워두고 나중에.

## 7. 한국어판

- 파일명은 원본 + `.ko`. (`0005-missing-server-behavior.ko.md`)
- `ko/` 디렉터리로 분리하지 않는다. 번호가 바뀔 때 짝이 안 보인다.
- 상단에 원본과 기준 커밋을 명시한다.

```markdown
> 이 문서는 [decisions/0005](./0005-missing-server-behavior.md)의 한국어판입니다.
> 기준: `6a8d0bc`. 두 문서가 어긋나면 영어판이 정본입니다.
```

- 한국어 문서의 경우 필수 작성 사항이 절대 아닙니다. 한국 독자의 이해를 돕기 위해 작성되며, 혹여 기여해주시고 싶은 마음이 있으시다면 AI를 통해 작성해서 보내주셔도 좋습니다. 리뷰 진행을 통해 수정될 수 있으며, 기여는 환영입니다!
