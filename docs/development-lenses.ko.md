# 다섯 가지 개발 관점

> **TL;DR** 정합성, 확장성, 신뢰성, 생산성, 지속 가능성은 smocket의 방향을
> 검토하기 위한 질문이지 점수나 작업 라벨이 아닙니다. 각 관점은 프로젝트의 범위,
> 근거, 차이점, 결정을 소유한 문서를 대체하지 않고 v1.0.0에 이르는 한 측면을
> 살펴봅니다.

아래 사례는 현재 프로젝트의 방식을 보여 주는 예시입니다. 지원 기능 전체나 각 관점의
작업이 완료되었다는 주장이 아닙니다.

## 정합성 (Fidelity)

- **의미.** smocket은 문서에 정한 [범위](./scope.ko.md) 안에서 관찰 가능한 동작과 공개
  타입을 측정된 Socket.IO와 일치시켜야 합니다. 확인하지 못한 동작을 추측하지 않고,
  의도적인 차이는 [ADR 0000](./decisions/0000-do-not-invent-what-has-no-source.md)에 따라
  명시합니다.
- **중요한 이유.** 애플리케이션이 Socket.IO 대신 smocket을 사용했다는 이유만으로 테스트에서
  다른 결과를 얻는다면 테스트 대역으로서의 가치가 약해집니다.
- **현재 사례.** [정합성 보고서](./conformance.md)는 양쪽 대상에서 실행한 사례로 생성됩니다.
  [차이점 목록](./differences.md)은 의도적인 차이, smocket 전용 API, 알려진 비의도적 차이를
  구분합니다.

## 확장성 (Extensibility)

- **의미.** 테스트 전용 기능은 smocket의 기본 호환 동작을 암묵적으로 바꾸지 않고 확장해야
  합니다. smocket 전용 표면은 별도로 구분하고 영향 범위를 제한합니다.
- **중요한 이유.** 테스트 기능 때문에 기본 경로를 신뢰하기 어려워지거나 사용 사례마다
  라우팅 코어를 수정해야 해서는 안 됩니다.
- **현재 사례.** [adapter 등록](./adapter-registration.md)은 라우팅을 확장 지점으로 제공하며,
  adapter가 선택적 스케줄링 훅을 사용하지 않으면 기본 전달은 코어에 남습니다.
  `DelayingAdapter`는 소켓 스트림의 순서를 바꾸지 않고 이 훅을 사용합니다. 자세한 결정은
  [ADR 0018](./decisions/0018-delivery-scheduling-adapter-hook.md)에 있습니다.

## 신뢰성 (Reliability)

- **의미.** 여기서 신뢰성은 변경 이후에도 약속한 결과를 반복 검증한다는 뜻입니다. smocket의
  [범위 밖](./scope.ko.md#재현하지-않는-것-신뢰성네트워크-계층)인 네트워크 안정성을 뜻하지
  않습니다.
- **중요한 이유.** 한 번 확인한 결과도 smocket, Socket.IO, 런타임, 테스트 스위트가 바뀌면
  회귀할 수 있습니다. 근거는 다시 실행할 수 있고 계속 동기화되어야 합니다.
- **현재 사례.** CI는 공유 동작 사례를 양쪽 대상에서 실행합니다.
  [정합성 보고서](./conformance.md#the-dual-run)는 두 대상이 모두 통과한 뒤에만 작성되며,
  생성된 보고서가 테스트 스위트와 달라지면 검사가 실패합니다.

## 생산성 (Productivity)

- **의미.** smocket은 Socket.IO 애플리케이션 테스트를 작성하고 변경하고 이해하는 데 필요한
  설정과 유지보수 비용을 줄이는 것을 목표로 합니다.
- **중요한 이유.** 동작의 정확성만으로는 mock 도입이 사용자의 테스트 흐름을 더 쉽게 만든다는
  사실이 입증되지 않습니다.
- **현재 사례.** [테스트 러너 통합 가이드](./test-runner-integration.md)는 애플리케이션 코드가
  `socket.io-client` import를 유지한 채 테스트에서 smocket으로 대체하는 방법을 보여 줍니다.
  이는 통합 경로이지 생산성 향상의 입증이 아닙니다. 실제 사용자 앱 및 handwritten mock과의
  비교는 아직 남아 있습니다.

## 지속 가능성 (Sustainability)

- **의미.** smocket의 공개 약속과 개발 방식은 v1.0.0 이후에도 관리할 수 있어야 합니다.
- **중요한 이유.** 유지할 수 없는 약속은 결국 문서, 테스트, 런타임 동작을 어긋나게 만듭니다.
  프로젝트는 무엇을 지원하고 어떻게 확인하는지 계속 설명할 수 있어야 합니다.
- **현재 사례.** [범위](./scope.ko.md), [정합성](./conformance.md), [차이점](./differences.md)은
  서로 다른 주장을 맡고, 반복되는 기술적 선택은 [결정 기록](./decisions/README.md)에 남깁니다.
  [ADR 0019](./decisions/0019-what-counts-as-a-breaking-change.md)는 공개 약속이 릴리스 분류에
  어떻게 영향을 주는지 정의합니다.
